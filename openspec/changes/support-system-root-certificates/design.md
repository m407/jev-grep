# Design

## Context

Мотивация — в [proposal.md](proposal.md), наблюдаемое поведение — в [delta](specs/jev-zen-integration/spec.md).

- `Cargo.toml:15` отключает defaults `reqwest` и включает `blocking`, `json`, `rustls-tls`; `Cargo.lock` закрепляет `reqwest 0.12.28`. Системного загрузчика в текущем графе нет.
- `src/api.rs:26–42` строит один клиент для обоих видов оценки; там уже запрещены redirects и встроенные retries. TLS использует defaults зависимости.
- `tests/test_cli.py:190–221` уже запускает локальный TLS-сервер и считает соединения при отказе доверия. Этот тест использует самоподписанный сертификат без SAN и поэтому не подходит как положительный сценарий.
- Выпуск собирает Linux GNU, macOS ARM64 и Windows MSVC; Python-проверки сейчас выполняются на Ubuntu. Новая матрица CI для этого небольшого изменения не требуется.
- Существующие требования транспорта и `bounded-api-retries` совместимы с добавлением корней. Требование минимального live-подтверждения Zen остаётся действующим; локальные TLS-тесты его не заменяют.

## Goals / Non-Goals

**Goals:** использовать уже предоставляемую `reqwest` загрузку корней, сохранив общий клиент и текущий TLS backend; получить доказательства отдельно для загрузки сертификатов и штатных хранилищ платформ.

**Non-Goals:** собственный обход файлов ОС, переключение TLS backend, пользовательские CA-флаги, отключение проверки сертификатов, поддержка клиентских сертификатов, горячая перезагрузка доверия и воспроизведение всех политик платформенного TLS-движка.

## Decisions

### 1. Добавить feature существующей зависимости

Включить `rustls-tls-native-roots` дополнительно к текущему `rustls-tls`, сохранив `default-features = false`. Обновить lockfile только для необходимого изменения графа, без намеренного обновления `reqwest` и прочих независимых пакетов. При штатной сборке изменение `Api::new` не требуется.

Проверены исходники именно закреплённой версии: [Cargo.toml v0.12.28](https://github.com/seanmonstar/reqwest/blob/v0.12.28/Cargo.toml) связывает `rustls-tls` с WebPKI, а дополнительную feature — с `rustls-native-certs`; [построение клиента](https://github.com/seanmonstar/reqwest/blob/v0.12.28/src/async_impl/client.rs#L686-L732) добавляет оба набора в один `RootCertStore`. Результаты Context7 не описывали нужную комбинацию достаточно точно, поэтому решение основано на этих исходниках.

Простая настройка текущего бинарника не помогает: загрузчик системных корней не включён. Замена WebPKI только системными корнями меняла бы прежнее доверие. Переход на `native-tls` затрагивал бы backend и платформенные зависимости без необходимости. Прямое подключение загрузчика и собственный TLS-конфиг дублировали бы существующую возможность `reqwest`; стандартная библиотека Rust не предоставляет эквивалентного HTTPS-клиента.

### 2. Доверие аддитивное и читается при создании клиента

Системные корни дополняют WebPKI. Удаление публичного CA из ОС не удаляет его из встроенного набора: это расширение текущего доверия, а не режим «только политика ОС». После установки CA пользователь запускает новый процесс.

Использовать штатное обнаружение загрузчика на Linux и штатные хранилища macOS/Windows. `SSL_CERT_FILE` и `SSL_CERT_DIR`, если заданы, переопределяют системный источник в `rustls-native-certs`; встроенные корни при этом сохраняются. Это поведение зависимости документируется, отдельная конфигурация приложения не добавляется. При проверке настоящего хранилища обе переменные должны отсутствовать.

Ошибки загрузки обрабатывает `reqwest`: пустой набор не отключает WebPKI; частично пригодные сертификаты используются. Нельзя обещать успешное построение клиента при произвольном повреждении хранилища: версия 0.12.28 возвращает ошибку, если загрузчик вернул сертификаты, но ни один не принят `RootCertStore`. Не вводить собственные fallback и предупреждения; существующий путь ошибки сохраняет код 2.

### 3. Расширить существующий TLS-тест, не создавать отдельную систему тестирования

В `tests/test_cli.py` переиспользовать HTTPS-сервер и счётчик соединений. Создавать временный CA с нужными расширениями и подписанный серверный сертификат с SAN `localhost`, назначением `serverAuth` и действительным сроком. Приватный ключ используется только локальным сервером и удаляется с временными файлами.

Обычная offline-проверка передаёт CA через `SSL_CERT_FILE`, изолирует `SSL_CERT_DIR` и прокси для loopback. Общий `clean_test_env` удаляет унаследованные CA-переопределения перед явными тестовыми overrides. Проверить одиночную и групповую оценку, отсутствие доверия, неверное имя и просроченный серверный сертификат. Для отрицательных случаев проверять код 2, одно TLS-соединение, ноль HTTP-запросов и отсутствие успешного результата, а не текст ошибки Rustls. Даты отрицательной фикстуры задавать явно в прошлом, без ожидания истечения срока и изменения часов ОС. Существующие проверки HTTP, redirects и retries остаются регрессионным покрытием.

Положительный тест с CA-файлом доказывает включение загрузчика, но не чтение хранилища ОС. По согласованному пересмотру приёмки проверка реальных хранилищ перенесена в последующую работу из-за отсутствия одноразовых окружений и не блокирует текущую приёмку. Контракт поддержки трёх ОС сохраняется, но его подтверждение реальными хранилищами остаётся пробелом в доказательствах; сборка и CA-файл этот пробел не закрывают. Последующая проверка использует тот же локальный сервер и CA на одноразовых Linux GNU/macOS ARM64/Windows MSVC окружениях: до установки CA отказ, после штатной установки и запуска нового процесса успех обоих видов оценки, после удаления и нового запуска снова отказ. На всех шагах `SSL_CERT_FILE`/`SSL_CERT_DIR` отсутствуют. Установку выполнять средствами конкретной ОС; не изменять хранилище рабочей машины разработчика. Фиксировать ОС, target, команды и результаты. Исходная незавершённая попытка записана в `verification.md`; она не становится успешной вследствие пересмотра плана.

Совместимость встроенных корней проверять графом features и небольшим существующим live-smoke через Zen с пустыми временными CA-файлом/каталогом. Это подтверждает публичную цепочку при отсутствии системных корней; нужны реальные credentials/API, отсутствие доступа фиксируется как незавершённая приёмка. Тела входа синтетические, ключ и ответы провайдера не сохраняются. Не создавать локальный тест, подменяющий встроенные публичные корни тестовым CA: он не проверял бы обычный бинарник.

Для реализации подходят `openspec-apply-change` и `find-docs` для сверки документации фактически разрешённой версии `rustls-native-certs`; текущее планирование не запускает эти проверки.

## Risks / Trade-offs

- ОС может содержать дополнительные корпоративные CA → доверие к ним является требуемым поведением; документация явно описывает объединение с WebPKI.
- CA-переменные окружения могут скрыть штатное хранилище → изолировать их в тестах и перечислить при диагностике в обеих версиях руководства.
- Повреждённое хранилище может привести к ошибке построения клиента → сохранить штатную проверку зависимости, не обходить TLS; обещание совместимости ограничено пустым источником, а не произвольными ошибками.
- Установка CA требует платформенного окружения и прав → последующая платформенная проверка использует одноразовые ОС и удаляет только тестовый CA; до её выполнения реальное системное доверие на трёх платформах остаётся непроверенным. Текущая приёмка ограничена локальным TLS-покрытием, общими offline-проверками и live-smoke Zen.

## Migration Plan

Выпустить бинарники с дополнительной feature и обновлённым lockfile. Данные и настройки приложения не мигрируют; для обычного использования достаточно установленного доверенного CA и нового запуска. Руководства EN/RU описывают проверку системного доверия и отличие CA-хранилища от keychain API-ключа. Откат — предыдущий бинарник либо возврат изменения features и lockfile; он снова перестаёт учитывать частные системные CA.
