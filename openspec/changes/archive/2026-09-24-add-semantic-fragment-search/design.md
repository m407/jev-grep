# Design

> Редакционная актуализация 2026-09-25 в рамках `migrate-to-jev-zen`: этот документ фиксирует исторический дизайн первоначальной реализации; опубликованные здесь измерения и конфигурации прежней модели не относятся к Jev.

## Context

Мотивация и границы изменения: [proposal.md](proposal.md). Основные specs пока отсутствуют; исходное поведение подтверждено `README.md`, `src/main.rs`, `src/search.rs`, `src/api.rs`, `tests/test_cli.py`.

Сейчас `search` объединяет чтение, HTTP-оценку и печать, хранит одну строку и нормализует CRLF до вызова модели. `Api` имеет один переиспользуемый blocking-клиент, но жёстко ожидает `answers.match.noul`. Acceptance-тесты используют Python standard library и локальный mock, не проверяют качество checkpoint. `Cargo.toml` уже содержит `serde`, `serde_json`, `reqwest`, `clap`, `ignore`, `anyhow`.

Исследование внешних контрактов:
- Историческое описание первоначального движка: он принимает несколько именованных вопросов к общему state и пакетно оценивает их; ответы не образуют последовательную цепочку рассуждений. Основано на upstream HTTP handler и Agent; это описание исходного периода, не контракта Jev.
- `ast-grep scan --json=stream` 0.45.3 проверен локально: выдаёт текст узла и UTF-8-диапазоны, сохраняет CRLF. `outline` не даёт тело узла, поэтому для первого адаптера не выбран. Код через stdin upstream читает до EOF; `lg` может потоково обрабатывать уже готовые JSONL-совпадения.
- agrind 0.19.6 по исходникам читает физические строки и не имеет сборщика multiline-событий; JSON не включает raw-текст автоматически. Поэтому он остаётся необязательным внешним извлекателем полей с явно сохранённым полем `text`, а не механизмом границ.

## Goals / Non-Goals

**Goals:**
- Сохранить простую последовательную обработку с одним pending логовым фрагментом и одной следующей записью, без фоновых задач и таймеров.
- Отделить исходный текст и координаты от модельных решений; оценка всегда относится к определённой версии текста.
- Переиспользовать текущий HTTP transport и обход файлов, а не строить отдельный pipeline framework.

**Non-Goals:**
- Автоматический запуск внешних CLI, установка моделей, собственные AST-грамматики, индекс и ранжированный top-K.
- Восстановление перемежающихся событий без идентификаторов, присоединение через пропущенные строки, повторное открытие upstream-файлов.
- Обновляемые результаты, завершение по паузе, автоматическое применение эвристик вместо недоступной модели.

## Decisions

### 1. Явный вход и независимый вывод

CLI получает `--input-format text|log-jsonl|ast-grep` (default `text`) и `--format human|json` (default `human`). `--json` остаётся псевдонимом, но его одновременное использование с `--format` отклоняется. Другие контракты опций находятся в [located-search-output](specs/located-search-output/spec.md).

Это одна программа с двумя стратегиями: text/log-jsonl используют модельную группировку, ast-grep — готовые кандидаты. Не нужен дополнительный `--mode`, который позволил бы противоречащие комбинации. Содержание не используется для автоопределения формата.

Существующая маршрутизация файлов/stdin остаётся в `main`; формат применяется к каждому физическому входу. Фильтры путей относятся к этим входам, не к upstream-полям `file`. Чтение text/log-jsonl завершается отдельно на каждом входном файле. В ast-grep метаданные счётчиков хранятся по upstream-источнику на весь запуск, что позволяет перемежающиеся записи.

### 2. Минимальный объект фрагмента и две системы координат

Небольшой общий тип результата (например, `src/fragment.rs`) содержит только данные общего output-контракта. Reader/adapters (например, `src/input.rs`) создают исходную запись с диапазоном. `src/search.rs` управляет pending-фрагментом и отбором; форматирование можно вынести в `src/output.rs`.

Для text байты считаются до decode и любых преобразований. LF и CRLF сохраняются в тексте и байтовом диапазоне; строки считаются по LF. Raw-записи конкатенируются без вставок. Для log-jsonl диапазон относится к физическим JSONL-строкам, а декодированные `text` соединяются дополнительным LF: `text_basis = decoded-records` делает это различие явным. Никакие произвольные metadata JSONL не объявляются координатами исходного лога до преобразования.

Для ast-grep используются upstream-диапазоны и `text`; поле `file = STDIN` переводится в `{kind: stdin, path: null}`, другие пути сохраняются как строки без canonicalize. Нулевые строки преобразуются в единичные. Для непустого текста, заканчивающегося LF, включительный `end_line` равен номеру upstream-конечной строки без добавления единицы; иначе добавляется единица. Проверки длины UTF-8, числа LF и порядка координат не требуют повторно читать файл. Они не доказывают актуальность upstream-файла и не могут проверить длину неизвестного префикса первой строки.

Human renderer показывает заголовок местоположения, отметки split и текст; обязательная построчная нумерация не нужна. Так не приходится придумывать номера для декодированного JSONL или префиксов части строки кода. Два участка одной строки кода различаются по байтовым диапазонам.

Альтернатива — единый JSONL-envelope для всех внешних инструментов — заставила бы пользователя преобразовывать нативный ast-grep JSON. Двух небольших явных адаптеров достаточно; произвольный mapping DSL не нужен.

### 3. Один запрос — четыре независимых решения

При первом фрагменте отправляется существующий вопрос `match` для его текста. Pending хранит текст, диапазон, последнюю оценку и `split_before`.

Для текущего фрагмента A и следующей записи B, если размер A+B допустим, отправляется один `POST /v1/systemone`:

```json
{
  "state": {"current_fragment": "A", "next_record": "B"},
  "questions": {
    "same_event": {"type": "noul", "instructions": "Does next_record continue the same concrete event as current_fragment? Shared topic alone is insufficient."},
    "useful_context": {"type": "noul", "instructions": "Does next_record materially explain, qualify, resolve, or contradict current_fragment with respect to the user criterion: <criterion>? Merely matching that criterion independently is insufficient."},
    "match_next": {"type": "noul", "instructions": "Evaluate only next_record, ignoring current_fragment. Criterion: <criterion>"},
    "match_extended": {"type": "noul", "instructions": "Evaluate current_fragment followed by next_record as one fragment. Criterion: <criterion>"}
  }
}
```

Это пример формы, не гарантия качества формулировок. Критерий вставляется в строковое значение через сериализацию JSON, не через ручное склеивание JSON. Поля state являются данными. Для joined-кандидата логическая последовательность и разделители соответствуют правилам text/log-jsonl.

API-клиент принимает ожидаемый набор question IDs и валидирует каждый `noul`; неизменяемые транспортные правила текущего клиента сохраняются. Групповые ответы преобразуются в небольшой типизированный результат без динамического исполнения инструкций.

После полной валидации:
- `same_event >= join_threshold OR useful_context >= join_threshold`: заменить A на A+B и его оценку на `match_extended`;
- иначе: завершить A с сохранённой оценкой; B становится новым pending с `match_next`.

Оценка A не пересчитывается с посторонней B. Вопросы не ссылаются на результаты друг друга. Отдельный `match_next` позволяет не делать второй запрос на каждой смысловой границе. По сравнению с двумя вопросами связи и отложенным `match` это увеличивает вычисления на присоединении, но даёт один последовательный round trip на очередную запись. Это выбранная проверяемая отправная точка, не обещание ускорения inference.

Низкая оценка pending не удаляет текст: позднее продолжение может сделать его релевантным. `--invert-match` применяется только при завершении. EOF использует актуальную сохранённую оценку, без дополнительного запроса. Для ast-grep выполняется только `match`.

### 4. Ограничение размера без скрытого обрезания

Новый `--max-fragment-bytes` default 16384 ограничивает оцениваемый UTF-8-текст, включая сохранённые/добавленные разделители. Это проектный default на основе текущего лимита строки, не измеренный размер контекста checkpoint. `--max-line-bytes` остаётся независимым пределом физической входной строки, включая JSONL-envelope; для большого ast-grep JSON пользователь увеличивает его явно. Обе опции проверяются на положительность и безопасное сложение.

До запроса с A и B проверяется размер расширенного кандидата. При превышении A завершается с `split_after=true`, B начинает новую часть с `split_before=true` и отдельно оценивается вопросом `match`. Признаки отмечают факт принудительной границы, а не обещают, что модель доказала принадлежность частей одному событию. Для цепочки нескольких частей внутренние части имеют оба признака. Они не зависят от того, прошла ли соседняя часть фильтр.

После завершения A сначала проверяются `-q`, `-l`, `-m`: если источник больше не нужен, отдельная оценка B не выполняется. Уже прочитанная B может быть lookahead; обещание «ни одного чтения после первого совпадения» не сохраняется.

Одна запись text/log-jsonl больше предела — ошибка, как и кандидат ast-grep: разрезание внутри строки/декодированного события/AST-узла потребовало бы иного контракта. Нормальный долгий лог разбивается только между допустимыми записями. Память ограничена размером pending, одной физической входной строкой, декодированным объектом, HTTP-ответом и буферами; для ast-grep дополнительно O(число встреченных источников) на счётчики, а не O(число кандидатов).

Байтовый предел не эквивалентен токенам. Исследованный HTTP handler первоначального движка не передаёт произвольный клиентский `max_len` в `router.predict`; добавлять в запрос неработающий параметр нельзя. Документация должна объяснять подбор предела под checkpoint и серверную настройку. Клиент не обрезает текст, но не обещает, что внешний сервер обработал все токены; это проверяется модельным экспериментом.

### 5. Ошибки и внешние процессы

Не меняются bearer, запрет redirects, TLS-проверка, тайм-аут HTTP, лимит ответа 64 KiB и exit 0/1/2. Ошибки чтения/модели не закрывают pending как успешный фрагмент. Уже выданный JSONL остаётся пригодным для чтения. Отдельный upstream-процесс не является дочерним процессом `lg`, поэтому его exit status проверяется shell через `pipefail`.

Нельзя молча терять записи из agrind: примеры документации сохраняют `text`, используют `nodrop` где применимо и объясняют, что отфильтрованные upstream-строки и их прежние координаты `lg` восстановить не может. Обязательный agrind не даёт преимуществ для raw-логов; пользователь может направлять их сразу в `lg`.

### 6. Проверка механики отдельно от качества модели

Существующий Python mock расширяется очередью ожидаемых запросов и ответов: одиночный `match`, четыре независимых решения, повреждённые ответы. Acceptance фиксирует OR-правило, границу равенства порогу, изменение релевантности после продолжения, корректное использование `match_next`/сохранённого score, EOF, паузу, лимит и раннюю остановку. Проверка до EOF синхронизируется с обработкой mock-запроса, а не только с произвольным sleep.

Координаты проверяются byte-oriented входами: кириллица, CRLF, LF, отсутствие LF в конце, несколько AST-узлов одной строки, escaped newlines в JSONL. Ожидаемые фрагменты и диапазоны сравниваются с исходными bytes. Проверки scalar/array вместо объекта, отрицательных/переполненных координат и лимитов выполняются до inference. Для code используются сохранённые тестовые JSONL-примеры; установка ast-grep не требуется в offline suite.

Для качества нужен отдельный небольшой воспроизводимый набор синтетических примеров: Gradle-like stack trace, npm-like ошибка с продолжением, Buildah-like шаг и вложенный вывод, retry с восстановлением, две соседние независимые ошибки. На реальном сервере фиксируются checkpoint/revision, prompt, лимиты, ошибки границ, качество отбора, latency и число запросов. Mock-тесты не подменяют этот отчёт; отсутствие доступного сервера обозначается как непроведённая модельная проверка, не как успех. Этот эксперимент не меняет контракт и не является основанием добавлять автоматический fallback.

Релевантные skills для реализации/проверки: `ast-grep` для upstream-фрагментов и fixtures, `find-docs` для актуального внешнего контракта, `HITL` для новых материальных решений, `openspec-apply-change` для выполнения задач.

## Risks / Trade-offs

- Ошибка OR-группировки может склеить тематически похожие события → проверять полезность относительно A, а не только запроса, иметь отдельный join-порог и конечный предел размера.
- Сервер может обрезать state, особенно его последнюю запись → ограничение клиента, документированная конфигурация checkpoint и проверка примеров у границы контекста; не обещать токенную гарантию по байтам.
- Вопросы `match_next`/`match_extended` могут влиять на качество через формулировки и общий state → разделённые инструкции и модельный набор с контрастирующими A/B; результаты тестов протокола не выдавать за точность.
- Отсутствие тайм-аута задерживает подходящий фрагмент при замолчавшем pipe → это согласованное поведение; показывать в help и проверять отсутствие преждевременного вывода.
- Принудительное разбиение теряет часть межфрагментного контекста → сохранить весь текст частями и маркировать обе стороны границы; не переносить score одной части на другую.
- ast-grep может выдавать вложенные/пересекающиеся узлы → сохранять их как отдельные upstream-кандидаты, документировать настройку правил вместо скрытой дедупликации.

## Migration Plan

1. Объявить breaking change относительно 0.1.0: фрагменты по умолчанию, отложенный логовый вывод, счётчики фрагментов, новая JSONL-схема, обязательное местоположение и отклонение `--no-filename`.
2. Обновить README/help и acceptance одновременно с реализацией, включая старый тест немедленной выдачи первой строки: заменить на ожидание смысловой границы и отдельную проверку ready-кандидата ast-grep.
3. Оставить `--json`, `-n`, `-H` с описанными правилами; не добавлять несогласованный legacy-режим. Сохранённый старый бинарник — путь отката для потребителей старой схемы.
4. Привести два конвейера с явным форматом и `pipefail`; raw-логи работают без agrind. Проверить текущую документацию первоначального движка перед описанием server tuning: `docs/deployment.md` содержит историческое исследование 0.3.7 и не доказывает нынешние свойства сервера.
5. Пройти offline checks и отдельно представить статус модельного эксперимента; не выполнять установку сервера или отправку приватных логов ради проверки по умолчанию.
