# Design

## Context

Мотивация и границы описаны в [proposal.md](proposal.md). Этот самостоятельный план применяется вместо `migrate-to-jev-zen`; прежние задачи/агенты не используются как prerequisites. Существующий change не редактируется данным planning-запуском.

Проверены `src/api.rs`, `src/main.rs`, `src/search.rs`, manifest/lockfile, Python acceptance-тесты, README, deployment guide и три основные specs. Клиент уже поддерживает нужные string/object state, именованные noul, bearer, атомарную проверку четырёх ответов, запрет redirects и лимит ответа 64 KiB. `Api::send` делает одну попытку; модель опциональна, defaults и имена требуют миграции. Тестовый HTTP-server сейчас преимущественно возвращает фиксированный статус; для retry нужны последовательности ответов. Старый experiment требует `/health`, содержит старые измерения и предположения о 512 токенах.

В lockfile закреплён reqwest 0.12.28. Его blocking client имеет встроенные повторы protocol NACK; RequestBuilder::timeout передаёт тайм-аут во внутренний async request. Один лишь client-level timeout не является достаточным обоснованием общего deadline при многократном `Read`: нужен timeout каждого request с остатком общего бюджета и тест медленно поступающего тела.

При финальной проверке planning-запуска рабочее дерево изменилось извне: появились переименование клиента/defaults, правки тестов/README/deployment, `fnox.toml` и отметка выполнения 1.2 старого change. Эти изменения не сделаны данным change и здесь не проверялись как реализация. Описание исходного состояния выше относится к началу исследования. Перед выполнением задач 1.1/1.2 перечитать текущий diff, переиспользовать уже готовое и выполнить их критерии, а не перезаписывать файлы. Чужие checkbox не переносятся автоматически; параллельное исполнение старого плана должно быть согласовано до apply нового. На момент проверки `src/api.rs` по-прежнему выполняет одну попытку.

Источники исследования на 2026-09-25:
- [Zen](https://opencode.ai/docs/zen/#jev), публичный `/zen/v1/models`: endpoint, bearer, `jev-1.13`/`jev-1.13-free`.
- [TypeSafe API](https://docs.typesafe.ai/api), [models](https://docs.typesafe.ai/models): shape ответа, два контекстных ограничения; лимиты прямого API не объявляются лимитами Zen.
- [fnox configuration](https://fnox.jdx.dev/reference/configuration.html), [keychain](https://fnox.jdx.dev/providers/keychain.html): exec-only, отсутствие plaintext ключа, локальный скрытый ввод.
- [reqwest 0.12.28 blocking client](https://github.com/seanmonstar/reqwest/blob/v0.12.28/src/blocking/client.rs), [request](https://github.com/seanmonstar/reqwest/blob/v0.12.28/src/blocking/request.rs), [response](https://github.com/seanmonstar/reqwest/blob/v0.12.28/src/blocking/response.rs): per-request timeout и управление встроенными retries; также проверена актуальная документация через Context7.
- [Исследованный jgrep](https://github.com/keltokhy/jgrep/tree/c4d929a0577425f1fe24bf2bd87de319855ac41e), [его transport](https://github.com/keltokhy/jevkit-core/blob/v0.3.2/src/jevkit_runtime/transport.py): источник идеи ограниченного retry, не зависимость проекта.

## Goals / Non-Goals

**Goals:** удержать конфигурацию и retry на существующей общей HTTP-границе, сохранить последовательность поиска и атомарность группировки; проверить миграцию существующей offline-инфраструктурой и небольшим live smoke.

**Non-Goals:** SDK/provider framework, async-переписывание поиска, встроенные Git/AST/diff readers, изменение промптов/порогов, новый quality runner. Estimate, методика качества, статистика, кэш и параллелизм ограничиваются записью в backlog.

## Decisions

### 1. Публичный интерфейс и контракт

Package/bin — `jev-grep`, env — `JEV_GREP_*`; названия флагов сохраняются. Модель становится непустой строкой с default `jev-1.13` и без optional omission в body. Ключ остаётся optional для mock/custom endpoint; штатный fnox-запуск требует его до старта процесса. Flags имеют приоритет над env. Не добавляем fallback или автоматический выбор бесплатной модели. Совпадение имени с Python distribution не меняет выбранное пользователем имя команды; тот проект устанавливает `jgrep`.

Внешний JSONL не расширяется `usage`/`model`. Дополнительные поля провайдера по-прежнему игнорируются, numeric noul остаётся достаточным контрактом. Новые runtime-проверки не требуют отдельного SDK. Простая установка env достаточна для предварительного подключения, но не заменяет согласованную миграцию публичного интерфейса и документации.

### 2. Одна retry-петля в общей точке отправки

Retry размещается в `src/api.rs` вокруг отправки и ограниченного чтения ответа. `probability`/`group_probabilities` сохраняют смысл и наборы вопросов. После полного тела JSON разбирается и валидируется без retry на ошибки содержания. Ошибки неполного транспорта до получения тела могут повторяться; предел размера проверяется до JSON parsing и не является retryable.

Политика фиксирована, без новых CLI-флагов: 4 попытки всего; HTTP 408/429/500/502/503/504/529; backoff перед повторами 200/400/800 ms плюс jitter 0..100 ms. `Retry-After` поддерживает целые секунды и HTTP-date. Серверное ожидание — нижняя граница, а не замена backoff. Пауза, не помещающаяся в оставшееся время, ведёт к немедленной окончательной ошибке. Заголовок с переполняющим числом секунд рассматривается как ожидание, не помещающееся в бюджет, а не разрешение быстрого повтора; неверный формат игнорируется. После четвёртой попытки sleep не выполняется.

Использовать `Instant` и вычитание elapsed из исходного бюджета, избегая переполнения `Instant + Duration` на огромном `--timeout`. Перед каждой попыткой и паузой проверяется остаток; request получает этот остаток через per-request timeout, который действует на внутренний поток тела. Повторное чтение не продлевает deadline. Сериализованный body переиспользуется или эквивалентно воспроизводится; endpoint/model/key неизменны. Каждый response освобождается перед sleep. Не читать неуспешное тело ради диагностики или reuse соединения: достаточно статуса и Retry-After, это также избегает неограниченного чтения error body.

Отключить встроенную reqwest retry policy (`retry::never()` доступна в закреплённой версии), чтобы прикладной лимит не умножался скрытыми повторениями клиента. Не обещать управление повторами внешних proxy/gateway. Временные сетевые сбои классифицировать по typed error/source chain: timeout, connection reset/refused/aborted, broken pipe, unexpected EOF; не повторять TLS validation, URL/header/request construction. Не считать любой `is_connect()` временным: он включает TLS failures. Не распознавать ошибки по тексту и не добавлять retry для неизвестной ошибки «на всякий случай».

`std::thread::sleep` и существующего reqwest достаточно для control flow. Для jitter использовать прямую зависимость `rand` с совместимой уже имеющейся lockfile-версией, а не самодельный генератор. Для HTTP-date добавить небольшой `httpdate`: в std нет HTTP-date parser; собственный календарный parser сложнее в сопровождении. Новые direct dependencies ограничены этими двумя, остальной lockfile не обновлять без необходимости. Конкретные вызовы API сверить с закреплёнными версиями при реализации.

Тестируемые небольшие helpers для классификации статусов и вычисления задержки могут получать текущее wall-clock время и jitter как значения; не создавать универсальные интерфейсы clock/sleeper/client. Реальные loopback-тесты покрывают завершение deadline и число отправок. Диагностика содержит номер попытки, последний HTTP-код или безопасный класс сетевой ошибки и причину остановки, не URL/query/key/error body.

Альтернатива middleware/async runtime не нужна для последовательных оценок. Немедленный fail-fast не покрывает подтверждённое требование retry. Неограниченные повторы и отдельный timeout каждой попытки нарушили бы ограничение времени команды.

### 3. fnox остаётся внешним launcher

При реализации создать корневой `fnox.toml`:

```toml
#:schema https://fnox.jdx.dev/schema.json
root = true
env = "exec"

[providers.zen-keychain]
type = "keychain"
service = "jev-grep"

[secrets]
JEV_GREP_API_KEY = { provider = "zen-keychain", value = "JEV_GREP_API_KEY", if_missing = "error" }
```

URL/model принадлежат defaults клиента, не конфигу секретов. Пользователь вводит ключ локально через `fnox set JEV_GREP_API_KEY --provider zen-keychain` без VALUE; запуск — `fnox exec -- jev-grep ...`. Конфиг содержит ссылку, а не plaintext/ciphertext. `.gitignore` исключает `fnox.local.toml`. Linux Secret Service может быть недоступен в текущей сессии: фиксируется blocker, хранилище не подменяется plaintext или age автоматически. `root=true` не исключает global fnox config; не обещать полную изоляцию.

### 4. Конвейер Git и AST — документация, не новая подсистема

Минимальный документированный сценарий: из корня репозитория сравнить рабочее дерево с `HEAD`, получить NUL-separated имена изменённых существующих Rust-файлов (`--name-only -z`, подходящий diff-filter), затем передать конкретные пути ast-grep с правилом `function_item` и `--json=stream`; результат направить в `jev-grep --input-format ast-grep`.

Пример пишется для Bash и явно задаёт: tracked изменения относительно HEAD, включая index+working tree, без untracked и удалённых файлов; читается именно рабочая версия исходников. Выбираются все функции изменённых файлов, а не только изменённые строки. Более точное пересечение с hunk-диапазонами не реализуется данным change. Поиск удалённой проверки требует old/new данных и не обещается этим конвейером.

Пути передаются NUL-safe и с защитой от имён-опций (`--` либо явный `./`), пустой список не превращается в запуск ast-grep по текущему каталогу. `pipefail` обязателен, но недостаточен для process substitution: ошибки Git также должны проверяться явно. При реализации использовать простой проверяемый Bash-пример с явным промежуточным списком/массивом и проверкой производителя; не помещать скрытый diff-parser в shell-пример. Проверить на временном fixture-репозитории вне исходного дерева: обычное изменение, путь с пробелами, удаления, пустой diff и Git failure. Для проверки end-to-end достаточно локального mock API, платный вызов не требуется.

### 5. Backlog и честная очистка истории рабочего дерева

`docs/BACKLOG.md` содержит пять разделов с краткой мотивацией и границей будущего scope:
- estimate: эвристика/диапазон, учитывающий зависимость логовых запросов от модельных границ;
- методика качества: границы/отбор, формулировки, языки, воспроизводимость; ссылка на сохранённый seed;
- статистика: реальные вызовы, retry, model/usage и время, без изменения текущего JSONL;
- кэш: identity endpoint/model/state/questions, различие alias и фактической версии;
- параллелизм: независимые AST-кандидаты и ограниченный ordered buffer; логовые зависимости сохраняются.

Сохранить полезные синтетические данные архивного experiment в `tests/fixtures/jev-quality-seed.jsonl`, нормализовав только прежние модельные labels/предположения и описав в backlog, что это неисполненный материал, а не evidence качества Jev. Не добавлять runner, метрики или corpus acceptance. После проверки переноса удалить старый experiment целиком с runner, отчётами и raw evidence. Сохранённые архивные planning-документы отредактировать без подмены исторической идентичности: краткая отметка editorial cleanup и нейтральная формулировка прежнего runtime, никаких утверждений о прошлом Jev-запуске. Исправить ссылки README/deployment/archive.

Основные specs синхронизировать из этого change штатным workflow при реализации. Старый альтернативный change и его агенты не удалять/не применять. Если итоговый аудит найдёт запрещённые строки в его project-owned файлах, это конфликт с требованием нулевых упоминаний: показать точные пути и запросить отдельное разрешение на необходимую редакционную очистку, не исключать их молча из проверки.

Аудит content/path: case-insensitive regex `l[a]ya`, tracked и untracked исходные файлы, включая `.opencode`, main specs, все активные/архивные changes. Исключения только `.git`, generated build/cache и установленные внешние dependencies. Сам regex не возвращает прежнее имя в исходники. Не менять пользовательские посторонние файлы без выяснения принадлежности. Старые `lg`/`LG_*` допустимы лишь в отрицательных тестах и явных migration-примечаниях; рабочие команды/ссылки/бинарники используют новый интерфейс.

### 6. Проверки и минимальный live smoke

Переиспользовать Rust unit tests и Python unittest с loopback mock; очистить оба env-префикса из дочернего окружения тестов. Проверить defaults/precedence/пустую модель/авторизацию, затем последовательности transient→success, permanent→stop, четыре ошибки, Retry-After seconds/date, превышение бюджета, disconnect и медленное тело. Проверки группировки закрепляют отсутствие преждевременного вывода и двойного изменения счётчиков. Паузы/jitter проверять диапазонами и helpers с заданным временем; не ждать реальные 30 секунд на каждую ошибку. Не менять production policy через неописанные env hooks ради тестов.

Live smoke после сборки и fnox: один синтетический AST-кандидат и ровно две короткие текстовые записи. Код 0 или 1 означает успешный проход модели, 2 — ошибка. Не использовать `-q`/`-m`, чтобы действительно достигнуть второй логовой записи. CLI выдаёт только прошедшие threshold фрагменты, поэтому результаты не обязаны включать все записи. Диагностическая запись в `docs/deployment.md` содержит дату, requested model/endpoint, воспроизводимые команды и outcome каждого случая; ключи и реальные пользовательские данные отсутствуют. Нового runner/benchmark-отчёта нет. При отсутствии доступа оставить live-задачу незавершённой, не ставить mock вместо Zen.

Для реализации релевантны `openspec-apply-change`, `ccc`, `find-docs`; для корректного ast-grep примера — skill `ast-grep`. Перед apply подготовить task-specific агентов именно этого change проектной командой; `agent=missing` не означает разрешение запускать старых агентов. Scope-only review каждой задачи обязателен по правилам проекта.

## Risks / Trade-offs

- [Повтор POST мог уже тарифицироваться до разрыва соединения] → ограниченные попытки и timeout, явное описание отсутствия exactly-once; статистика расходов отложена.
- [TLS failure выглядит как connection error] → typed классификация причин и отрицательные тесты, неизвестные ошибки не повторяются.
- [Retry-After date зависит от wall clock] → пересчитать задержку один раз по SystemTime, общий бюджет отслеживать монотонно.
- [Новый бинарник ломает shell-конвейеры] → обновить примеры и тесты, не удалять старые executables из пользовательского PATH автоматически.
- [Smoke не доказывает качество новой модели] → сохранить пороги/промпты, не заявлять улучшение точности; методика в backlog.
- [Два активных альтернативных change] → явно выбирать этот полный план, не выполнять старый параллельно; существующие агенты принадлежат старому плану.

## Migration Plan

1. Переименовать клиент и закрепить defaults; независимо подготовить fnox/deployment guide.
2. Внедрить retry в общий API boundary и проверить transport/fragment contracts.
3. Обновить README и diff-конвейер, создать backlog, перенести seed, очистить архив и синхронизировать main specs.
4. Провести итоговые offline-проверки и два live smoke-сценария при доступном ключе. Недоступность ключа — конкретный blocker live-приёмки.
5. Откат — отдельный согласованный revert implementation-коммитов; keychain entry автоматически не удаляется. Откат публичного интерфейса также отменяет критерий миграционной очистки до повторного применения.
