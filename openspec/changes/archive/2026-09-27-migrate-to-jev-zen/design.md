# Design

## Context

Мотивация и согласованные изменения описаны в [proposal.md](proposal.md). Design нужен из-за сквозной миграции публичного интерфейса, внешнего gateway, хранения ключа и исторических материалов.

Проверены `src/main.rs`, `src/api.rs`, Cargo manifest, acceptance-тесты, README, deployment guide и архивный эксперимент. Клиент уже отправляет JSON System One и читает `answers.<id>.noul`. Он использует blocking reqwest с reuse соединения, запретом redirects, timeout и пределом ответа 64 KiB. `model` сейчас опционален; Python-тесты закрепляют старый путь бинарника и очищают старый env-префикс. Архивный runner требует `/health`, делает прямые probes без bearer и интерпретирует длинный случай относительно старого 512-токенового бюджета.

В ходе исследования 2026-09-25 публичный GET Zen `/zen/v1/models` вернул `jev-1.13` и `jev-1.13-free`. Live inference ещё не выполнялся. fnox установлен, проектного конфига нет; доступность системного keychain пока не подтверждена.

Источники для принятых контрактов:
- [Zen: endpoint, ID модели, bearer и цены](https://opencode.ai/docs/zen/#jev).
- [TypeSafe HTTP API](https://docs.typesafe.ai/api): строковый/объектный state, параллельные вопросы и ответы noul.
- [Jev models](https://docs.typesafe.ai/models): контекст 64k для state и всех вопросов, одновременно 32k для state и самого длинного вопроса.
- [Ограничения Jev 1.13](https://docs.typesafe.ai/model-jaggedness/jev-1.13): буквальная интерпретация, нерелевантный контекст и языковая вариативность.
- [fnox configuration](https://fnox.jdx.dev/reference/configuration.html), [keychain](https://fnox.jdx.dev/providers/keychain.html); локальный `fnox set --help` подтверждает скрытый ввод без аргумента VALUE.

## Goals / Non-Goals

**Goals:**
- Свести runtime-изменения к конфигурационной границе существующего HTTP-клиента и проверить совместимость на реальном Zen.
- Сделать переименование и удаление исторических результатов проверяемыми, не приписывая новой модели старые измерения.
- Разделить детерминированные offline-проверки клиента и эмпирическую оценку модели.

**Non-Goals:**
- Новый SDK, provider abstraction, choice/score, parallel inference, retry/backoff, cache или изменение алгоритма группировки.
- Автоматическое изменение порогов/промптов ради прохождения нового корпуса, увеличение лимита фрагмента либо добавление токенизатора.
- Переписывание Git history, установка локального inference-сервера или автоматическое создание API-ключа.

## Decisions

### 1. Один клиент, явная модель и согласованный интерфейс

В `Cargo.toml` менять package/bin на `jev-grep`, соответствующее имя root package обновить в lockfile без обновления зависимостей. В `Args` модель сделать строкой с default `jev-1.13`, в `request_body` включать её без optional-ветки. Проверять непустое имя после trim без преобразования самого ID. Сохранить флаги и precedence clap: flag > новый env > default. Env-префикс `JEV_GREP_*` выбран как прямое отображение имени команды; это проектное решение, а не требование Zen.

API-ключ остаётся опциональным на уровне общего транспорта для mock/custom endpoint. Zen получает bearer, когда ключ задан, и его ошибка авторизации остаётся обычной HTTP-ошибкой. Штатный fnox-запуск требует секрет до старта клиента. Значения ключа скрыты в help; диагностике достаточно HTTP-кода. Добавлять отдельный cloud/local режим или credential fallback нет необходимости.

Существующие request shapes и инструкции сохраняются для первого эксперимента. Дополнительные `type`, `model`, `usage` не требуют изменения JSONL поиска. Метаданные для эксперимента собираются его probes, а не новым флагом клиентской телеметрии. Проверку чисел и атомарную обработку четырёх ответов переиспользуем. Строгую обязательность `type` в ответе не вводим: существующий контракт опирается на numeric `noul` и допускает дополнительные поля.

Альтернатива «только env-настройки» достаточна для smoke-запуска, но не для согласованной миграции defaults и имени. Новый SDK не добавляет необходимой функциональности. `jev-latest`, `jev-1.13.0` и `opencode/jev-1.13` не подставляются вместо подтверждённого Zen ID. Free ID доступен только явным override.

### 2. fnox — внешний launcher с одним keychain-секретом

Создать в корне следующую конфигурацию при реализации:

```toml
#:schema https://fnox.jdx.dev/schema.json
root = true
env = "exec"

[providers.zen-keychain]
type = "keychain"
service = "jev-grep"

[secrets]
JEV_GREP_API_KEY = { provider = "zen-keychain", value = "JEV_GREP_API_KEY", if_missing = "error" }
```

URL и model не дублируются в fnox: defaults принадлежат клиенту; runner ниже также использует задокументированные defaults. Ключ вводится пользователем в терминале через `fnox set JEV_GREP_API_KEY --provider zen-keychain` без VALUE. Пример запуска — `fnox exec -- jev-grep --json 'Certificate validation failure' sample.log`. В репозитории никогда не требуется реальный секрет; `fnox.local.toml` добавляется в `.gitignore`.

Для одного локального ключа keychain проще age: не требуется генерировать и распространять private identity. На Linux проверяется Secret Service, затем документируется конкретный blocker, если его нет. Автоматического plaintext fallback нет. Переход на age требует отдельного решения, а не молчаливой смены способа хранения при реализации. `root = true` прекращает поиск в родительских каталогах, но не исключает глобальный fnox config; это не обещание полной изоляции окружения.

### 3. Актуальный эксперимент за пределами исторического change

Разместить корпус, runner и отчёт в `experiments/jev/`. Переиспользовать смысловые примеры из архивного `experiment/dataset.jsonl`, добавить заранее заданные query и ожидаемые выбранные диапазоны, AST JSONL, русский/смешанный пример. Длинную строку назвать `long-input`: удалить из её разметки старые предположения про checkpoint/512 токенов. Сохранить отдельный byte-edge пример как проверку клиентского разбиения.

Runner — небольшой Python-скрипт `experiments/jev/run.py` на standard library, уже доступной для тестов проекта. Это заменяет shell/jq/curl-связку, позволяет передавать Authorization в памяти без process arguments и унифицировать probes с учётом errors. Запуск: `fnox exec -- python3 experiments/jev/run.py --bin target/release/jev-grep`. Runner не собирает бинарник и не устанавливает зависимости. Defaults — Zen/`jev-1.13`; переопределения читаются из `JEV_GREP_API_URL`, `JEV_GREP_MODEL`, ключ — только из `JEV_GREP_API_KEY`. Выходной каталог свежего запуска задаётся `--out`, чтобы прошлые успешные артефакты нельзя было выдать за текущий запуск.

Перед корпусом runner выполняет авторизованные синтетические POST: строковый state с `match` и объектный state с четырьмя вопросами. Ответы подтверждают wire compatibility и содержат фактические model/usage. Дополнительный probe длинного входа фиксирует usage; без знания токенизации это измерение длинного входа, не утверждение о заполнении контекста. Не вызывать `/health` и не требовать старое поле `routing`.

Далее runner вызывает настоящий бинарник на каждом случае, сохраняет stdout, stderr, exit и wall latency, сравнивает выбранные диапазоны с разметкой. Клиент остаётся без телеметрии: количество его запросов вычисляется только для успешного прохода согласно существующему потоку (один запрос на оцениваемую запись); при ошибке число неизвестно. Прямые probes считаются фактически; usage для них не объявляется usage всего корпуса. В отчёте эти источники измерений явно различаются. Сохранять только нужные поля ответов, без HTTP-заголовков; не печатать environment и секреты.

Offline-проверка runner использует существующий подход локального HTTP mock и стандартный unittest: bearer на каждом probe, отсутствие `/health`, отказ при неполном ответе/ошибке и корректная фиксация blocker. Live-запуск на синтетике обязателен для завершения задачи эксперимента; при отсутствии ключа он ждёт пользователя. Acceptance не требует нулевых ошибок модели: нужен полный честный отчёт. Изменение промптов или порогов по результатам становится отдельным решением.

### 4. Очистка без фальсификации исторических материалов

В архивном change удалить старые `experiment/RESULTS.md`, `experiment/evidence/` с измерениями и старый runner после переноса полезного корпуса. Осмотреть весь `experiment/`, перенести только нужные данные, затем удалить оставшиеся неактуальные файлы. В сохранённых proposal/design/tasks и delta-specs убрать ссылки на прежний runtime и старые измерения; добавить краткую отметку редакционной актуализации в рамках текущего change. Она не утверждает, что историческая реализация или измерения выполнялись на Jev. Идентификаторы архивных задач и их статус не превращать в evidence нового live-запуска; текущая задача эксперимента начинается невыполненной.

README и deployment guide переписать по актуальному контракту, все команды перевести на новое имя и env-префикс. Ссылки на старый эксперимент заменить новой методикой/отчётом. Удалить заявления о локальных весах, server routing и прежнем контексте. Для цен и model limitations указать дату и первоисточник; throughput прямого TypeSafe API не обещать как лимит Zen.

Основные specs обновить штатным sync delta-specs при реализации, до итогового аудита дерева: иначе нормативная старая привязка останется до archive. Существующие неизменённые требования `located-search-output` не дублировать.

Проверка очистки не должна сама возвращать запрещённое имя в исходники. Для content/path audit использовать case-insensitive regex `l[a]ya` (совпадает с прежним четырёхбуквенным именем), с выводом только путей. Проверяются tracked и новые исходные файлы, включая `.opencode` и все `openspec/changes`; исключаются только `.git`, генерируемые build/cache и установленные внешние зависимости. Проверять также имена файлов и каталогов. Нельзя исключить архив или собственный новый change ради зелёного результата. Старые строки в Git object database не очищаются. Любые сторонние локальные файлы сначала идентифицировать, а не удалять массово.

### 5. Проверки на существующей инфраструктуре

Тесты `src/api.rs` и `tests/test_cli.py` покрывают необходимые границы: defaults без сети, precedence flag/env, explicit model, пустой model, игнорирование прежнего env, bearer и типичные ответы Zen с metadata, HTTP 401/429/529. Обновить путь бинарника и очистку окружения тестового harness. Чистота окружения включает оба префикса, чтобы тесты не унаследовали пользовательские credentials. Все штатные acceptance-тесты обращаются только к loopback mock.

Существующие проверки координат, группировки, лимитов и ошибок переиспользуются. Повторная проверка завершается командами из tasks; новые тесты не копируют механику rename. Для подготовки task-specific агентов применяется проектная команда; для реализации подходят skills `openspec-apply-change`, `ccc` для поиска и `find-docs` для актуальных внешних контрактов. Review выполняется по фактическому scope задачи.

## Risks / Trade-offs

- [Документация API не равна live-подтверждению Zen] → два обязательных авторизованных smoke-запроса перед полным корпусом, наблюдаемая model metadata в отчёте.
- [Keychain недоступен из agent/SSH-сессии] → проверка доступа, локальный ввод пользователем и честный blocker live-задачи; config может быть готов без сохранённого секрета.
- [Новые имена ломают пользовательские shell-конвейеры] → единое обновление всех примеров; старые бинарники в пользовательском PATH автоматически не удаляются.
- [Та же вероятность не означает то же качество после смены модели] → исходные thresholds сохраняются, ошибки и языковые случаи фиксируются новым экспериментом.
- [Удаление архивных evidence уменьшает доступность старых измерений в рабочем дереве] → это явное решение пользователя; исходные факты остаются в Git history.
- [Отсутствие retries прерывает длинный проход при rate limit] → сохранить понятный HTTP status и fail-fast контракт; retry-политику не добавлять без отдельного требования.

## Migration Plan

1. Перевести runtime и offline-тесты на новый интерфейс; параллельно подготовить fnox-конфиг в независимых файлах.
2. Перенести корпус и подготовить новый runner; затем актуализировать документацию/архив и синхронизировать delta-specs.
3. Собрать release-бинарник, настроить ключ локально, выполнить live-корпус и оформить реальные результаты, исправить ссылки на отчёт.
4. Выполнить итоговый аудит исходного дерева, offline-проверки и OpenSpec validation. Не считать отсутствие live-доступа успешным экспериментом.
5. При необходимости отката вернуть исходные файлы через отдельный Git revert согласованного implementation commit; keychain-ключ автоматически не удалять. Откат возвращает прежнее состояние, поэтому также отменяет критерий чистого Jev-дерева до следующей миграции.
