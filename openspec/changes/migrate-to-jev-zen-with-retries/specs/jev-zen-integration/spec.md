# Spec Delta

## Purpose

Обеспечить воспроизводимое использование Jev через OpenCode Zen в CLI поиска фрагментов с согласованными именами, конфигурацией, локальным ключом и документацией.

## ADDED Requirements

### Requirement: Единый публичный интерфейс Jev

Пакет Cargo и единственный устанавливаемый бинарник SHALL называться `jev-grep`. CLI SHALL использовать `JEV_GREP_API_URL`, `JEV_GREP_MODEL`, `JEV_GREP_API_KEY` и сохранять флаги `--api-url`, `--model`, `--api-key` с приоритетом flag > env > default. Default endpoint SHALL быть `https://opencode.ai/zen/v1/systemone`, default model — `jev-1.13`; модель SHALL передаваться в каждом запросе и не быть пустой/пробельной. Старые бинарные и env-алиасы SHALL NOT поддерживаться. Пороги, размеры фрагмента, форматы входа/вывода и инструкции вопросов сохраняются.

#### Scenario: Запуск с defaults
- **WHEN** endpoint и модель не переопределены
- **THEN** клиент выбирает Zen и отправляет `model=jev-1.13`, а help/version называют `jev-grep`

#### Scenario: Явное переопределение
- **WHEN** заданы env URL/model и отличающиеся флаги URL/model
- **THEN** используются значения флагов, включая явно выбранный `jev-1.13-free`

#### Scenario: Пустая модель
- **WHEN** effective model пуст или состоит из пробелов
- **THEN** CLI завершается кодом 2 до HTTP-запросов

#### Scenario: Прежнее окружение
- **WHEN** заданы только переменные прежнего CLI
- **THEN** они не изменяют endpoint/model и не используются как источник ключа

### Requirement: Совместимый System One транспорт

Клиент SHALL отправлять JSON с `model`, `state`, `questions` и bearer-ключом, если ключ задан. Строковый state с `match` и объектный state с четырьмя вопросами SHALL сохраняться. Каждый обязательный `answers.<id>.noul` SHALL быть конечным числом в [0,1]; все четыре ответа проверяются до применения результата. Дополнительные metadata игнорируются; отдельная обязательность поля `type` не вводится. Сохраняются предел ответа 64 KiB, проверка TLS, запрет redirects и credentials в URL. Диагностика SHALL NOT раскрывать ключ или тело ответа провайдера. Отсутствие ключа допустимо для custom/mock endpoint; оно не вызывает fallback к другому endpoint.

#### Scenario: Ответ Jev с метаданными
- **WHEN** API возвращает корректные noul вместе с `model`, `usage` и дополнительными полями
- **THEN** клиент применяет noul по существующим правилам, не добавляя metadata в JSONL результатов

#### Scenario: Неполная групповая оценка
- **WHEN** успешный HTTP-ответ не содержит одного из четырёх корректных noul
- **THEN** оценка завершается ошибкой 2 без применения частичного результата и без повторного запроса

### Requirement: Тестовый ключ через fnox

Проект SHALL содержать `fnox.toml` со ссылкой на OS keychain для `JEV_GREP_API_KEY`, exec-only injection и ошибкой при отсутствии секрета. Конфиг SHALL NOT содержать реальный ключ. Руководство SHALL описывать скрытый интерактивный ввод через `fnox set`, запуск через `fnox exec`, требование Linux Secret Service и конкретную диагностику недоступного хранилища без plaintext fallback. `fnox.local.toml` SHALL быть исключён из Git. Defaults URL/model принадлежат CLI и не дублируются в fnox.

#### Scenario: Отсутствующий секрет
- **WHEN** штатный fnox-запуск не может получить требуемый ключ
- **THEN** child не запускается, а пользователь получает ошибку настройки хранилища

#### Scenario: Настроенный ключ
- **WHEN** пользователь сохраняет ключ в keychain и запускает клиент через fnox
- **THEN** клиент получает `JEV_GREP_API_KEY`, а tracked конфиг хранит только ссылку на запись хранилища

### Requirement: Актуальные материалы и отложенные направления

Все исходные материалы текущего дерева, включая скрытые проектные файлы, основной OpenSpec и архив, SHALL не содержать прежнего имени модели в содержимом и путях; проверка использует case-insensitive regex `l[a]ya`. Исключаются Git object database, build/cache и установленные внешние зависимости. Фактические старые отчёты, raw evidence и неактуальный runner SHALL удаляться, а не приписываться Jev. Полезный синтетический корпус SHALL сохраняться отдельно как неисполненный seed для будущей оценки, без старых результатов и предположений о контексте. Руководство SHALL описывать Zen, его модельные ID, отправку текста удалённому API и retry. `docs/BACKLOG.md` SHALL содержать ровно пять согласованных направлений: estimate, методика оценки качества, статистика, кэш ответов, параллелизм; ни одно не объявляется реализованным данным change.

#### Scenario: Аудит дерева после миграции
- **WHEN** проверены пути и содержимое исходных файлов, включая OpenSpec и скрытые project-owned файлы
- **THEN** regex не находит совпадений, удалённые материалы не имеют битых локальных ссылок, а старые измерения нигде не названы результатами Jev

#### Scenario: Backlog вместо расширения scope
- **WHEN** пользователь открывает backlog
- **THEN** видит пять отложенных направлений с мотивацией и границами, а live smoke не описан как подтверждение качества модели

### Requirement: Минимальное live-подтверждение Zen

При приёмке SHALL быть выполнена небольшая проверка настоящего клиента через Zen с синтетическим одиночным кандидатом и парой логовых записей, упражняющей групповую оценку. SHALL фиксироваться дата, requested model, endpoint, команды и итог протокольного успеха без ключа; полнота benchmark-корпуса, latency/usage статистика и качество границ не являются критериями. При отсутствии ключа/API live-проверка SHALL оставаться невыполненной с конкретной причиной; mock SHALL NOT выдаваться за live.

#### Scenario: Нет live-доступа
- **WHEN** ключ или Zen недоступен при приёмке
- **THEN** offline-результаты сохраняются, но live-задача не отмечается выполненной

#### Scenario: Протокол подтверждён
- **WHEN** оба синтетических сценария завершаются через Zen без ошибок входа/API
- **THEN** smoke подтверждает совместимость одиночной и групповой оценки независимо от того, какие фрагменты модель отобрала
